# CityWatch as a Slack bot — research, October 17, 2026

Implementation decision after this research: the user selected Bike Easy's `#policy-design` and asked for digest-only delivery, leaving replies as a future possibility. The first release therefore uses the Slack Web API with a bot token and only `chat:write`; it has no Socket Mode connection or commands. See [setup](../docs/slack-setup.md). The original interactive options below remain background research.

Recommendation: for one workspace, use a custom Slack app built with Bolt for Python and Socket Mode, hosted alongside the existing Coolify worker. Start with a daily digest and explicit search/status commands. Natural-language answers are an optional later layer. This is research, not an approved implementation plan; no Slack app, credentials, or messages have been created.

## Options

| Option | What it provides | Fit |
| --- | --- | --- |
| Incoming webhook | Scheduled posts into the channel chosen during installation; supports Block Kit formatting. | Smallest addition if the only requirement is receiving alerts. Does not by itself receive commands or questions. |
| Bolt + Socket Mode | Digests, slash commands, mentions, buttons, and replies over an outbound WebSocket connection. | Recommended for an internal CityWatch bot. No public request endpoint is needed. |
| Bolt + HTTPS Events API and OAuth | Public request endpoints, installations and credentials per workspace. | Appropriate if the intended product is distributed across independent workspaces or listed in the Marketplace. More installation and tenant-isolation work. |

Slack documents [incoming webhooks](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/), [Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/), and the [Python Bolt adapter](https://docs.slack.dev/tools/bolt-python/concepts/socket-mode/). Socket Mode currently prevents public Slack Marketplace listing; this is not a limitation on the proposed internal bot.

## What is already reusable

The repository already collects official sources, extracts documents, matches topics, tracks revisions, saves evidence, groups updates, and persists an outbox in SQLite. `citywatch/core.py` supplies records and matching; `citywatch/preview.py` groups digest evidence; `citywatch/mail.py` implements durable email batches; `citywatch/service.py` runs collection on Coolify with a persistent volume.

Slack needs its own renderer and delivery adapter. The existing global outbox status is consumed by email, so adding Slack directly to `pending()` would make destinations compete for alerts. Delivery state must instead distinguish the revision, workspace/channel, and transport, with separate batches, attempts, cadence, and acknowledgements. Keep email history and existing retry guarantees during that migration. Save Slack channel/message IDs for threaded replies and recovery after partial delivery. Ambiguous timeouts still require reconciliation; do not claim exactly-once delivery.

The command listener should run separately from lengthy collection/OCR jobs. It can use the same persisted data on this host, with explicit SQLite concurrency/locking behavior. Commands should acknowledge promptly and perform slower work afterward: Slack's [slash-command deadline is three seconds](https://docs.slack.dev/interactivity/implementing-slash-commands/).

## Proposed experience to evaluate in planning

- One daily summary in a designated channel; details grouped by meeting/document in threads, retaining excerpts, dates, page references, source links, and coverage warnings.
- `/citywatch search waymo` searches saved evidence and explains whether a result was collected, matched, queued, or delivered.
- `/citywatch status` shows the most recent scan, failures by source, and pending deliveries.
- `/citywatch digest` previews the current digest privately unless the user explicitly chooses to post it.
- Optional `@CityWatch` questions later. Search and status do not require an LLM. Freeform synthesis would need grounded retrieval, citations, evaluation, and a model/cost decision.

Slack allows [50 blocks per message](https://docs.slack.dev/reference/block-kit/blocks/). [`chat.postMessage`](https://docs.slack.dev/reference/methods/chat.postMessage/) recommends short text, supports thread replies, and requires an accessible text fallback when using blocks. Use bounded sections and split long digests deliberately. Respect [rate limits and `Retry-After`](https://docs.slack.dev/apis/web-api/rate-limits/); posting is generally limited to about one message per second per channel. Avoid unnecessary link previews and channel-wide notifications.

## Slack setup required

For the recommended internal app:

- A workspace where the app can be installed, workspace approval if its policy requires it, and a destination channel with the bot invited.
- Bot token with `chat:write` and `commands`; add `app_mentions:read` and the `app_mention` event only if mentions are included.
- An app-level token with `connections:write` and Socket Mode enabled. Store both tokens in Coolify secrets.
- A channel ID, allowed workspace/user policy for any administrative commands, and a separate test channel for rollout.

These permissions follow Slack's [Socket Mode setup](https://docs.slack.dev/apis/events-api/using-socket-mode/), [commands scope](https://docs.slack.dev/reference/scopes/commands/), and [`chat.postMessage` scopes](https://docs.slack.dev/reference/methods/chat.postMessage/). The proposed commands query CityWatch's own data; broad Slack conversation-history access is unnecessary. Do not implement arbitrary fetched URLs or silently change monitoring rules from a chat message.

## Reliability dependency

Moving delivery into Slack does not improve collection coverage. The email audit found incomplete coverage in every production digest reviewed, including a Council feed parse failure. A bot must say “not found in collected evidence; coverage incomplete” when appropriate, rather than “no such motion.” Repairing source coverage should be considered alongside the bot work. The matching and presentation changes can be reused independently.

## Decisions needed before planning

1. One internal workspace, or a product for other workspaces?
2. Digest delivery alone, explicit search/status commands, or conversational questions too?
3. Slack alongside email, or replacing email? Daily digest, immediate alerts, or a mix?
4. Which channel and who may change subscriptions, trigger scans, or post a digest?

No additional database service is inherently required for a single-host, single-workspace version. A reliable dual-channel bot needs delivery-state migration, reconnect/retry handling, message-size tests, replay/duplicate checks, and operational visibility; it is more than a webhook POST.
